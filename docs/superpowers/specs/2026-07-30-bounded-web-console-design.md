# Web Console 有界日志窗口设计

## 背景

Web 首页的 Console 当前会在打开时加载任务的全部历史日志，并为每条日志同时保留一份
JavaScript 字符串和一个独立的 DOM 节点。实时日志到达后继续无限追加；启用自动滚动
时，每条日志还会触发布局读取和滚动写入。关闭抽屉只会断开 SSE，不会释放已经保留的
日志数据。

这使浏览器内存、DOM 数量和布局成本随任务日志量持续增长。在配置较低的电脑上，
Console 长时间打开或载入大任务历史时可能导致页面卡死。

## 目标

- Console 在浏览器中最多保留并渲染最近 200 条日志。
- 完整日志继续持久化在服务端，不因前端窗口限制而丢失。
- 用户可以下载任务的完整日志。
- 历史加载和实时日志使用同一个 200 条滑动窗口。
- 一批日志只进行一次 DOM 提交和一次自动滚动。
- 关闭、切换或重复打开 Console 时，不残留请求、定时渲染或 SSE 连接。
- 保持现有日志级别颜色、连接状态和自动滚动开关。

## 非目标

- 不删除或自动清理数据库中的历史日志。
- 不实现可配置的前端窗口大小。
- 不引入前端框架、虚拟列表库或 Node.js 构建流程。
- 不改变任务执行和日志采集方式。
- 不在 Console 中提供任意历史区间翻页。

## 方案比较

### 方案一：有界滑动窗口

只请求最近 200 条历史日志，实时新增时从窗口头部淘汰旧日志。完整日志通过单独下载
接口获取。

优点是内存和 DOM 成本有明确上限，实现简单，低配电脑上的行为可预测。缺点是 Console
中不能向上滚动查看 200 条以前的日志。

### 方案二：虚拟列表

浏览器保存全部日志，只渲染当前可见区域。

它支持完整的页面内历史浏览，但 JavaScript 内存仍随日志量增长，还需要处理动态行高、
滚动定位和实时追加，复杂度明显更高。

### 方案三：单一文本节点

把全部日志拼接为一个文本节点，减少 DOM 节点数量。

它会失去按日志级别着色的简单实现，并且字符串和文本布局仍然无限增长，不能从根本上
提供资源上限。

采用方案一，窗口大小固定为 200 条。

## 服务端设计

### 最近日志

保留现有 `GET /tasks/{task_id}/logs?after_id=<id>` 的正向分页语义，供 SSE 补发和其他
现有调用继续使用。

新增 `GET /tasks/{task_id}/logs/recent`，固定返回该任务按 ID 排序的最近 200 条日志。
数据库查询先按 ID 倒序限制 200 条，再在返回前恢复为正序。任务不存在时返回 404。

固定窗口而不是接受任意 `limit`，避免客户端误请求过大的历史集合，也让性能边界成为
接口契约。

### 完整日志下载

新增 `GET /tasks/{task_id}/logs/download`，以附件形式返回 UTF-8 的纯文本日志。内容按
日志 ID 正序生成，每行格式为：

```text
[LEVEL] message
```

响应通过分批读取数据库并流式输出，不把完整日志一次性加载到服务端内存。任务不存在
时返回 404。下载文件名使用任务 ID，不使用用户上传的文件名。

数据库和 `task.log` 的现有持久化不变；前端窗口淘汰只影响浏览器展示。

## 前端设计

### 打开流程

打开 Console 时：

1. 关闭已有 SSE。
2. 取消上一轮历史请求和待执行的动画帧。
3. 清空 DOM、日志字符串、待渲染队列和游标。
4. 创建本轮打开操作的唯一版本号和 `AbortController`。
5. 请求 `/tasks/{task_id}/logs/recent`。
6. 确认响应仍属于当前打开操作后，把历史日志加入待渲染队列。
7. 从最后一条历史日志 ID 建立 SSE；在历史请求期间新增的日志由 SSE 从该 ID 后补发。

版本号同时保护成功和失败回调，过期操作不得修改标题、连接状态或建立新 SSE。

### 有界缓冲

前端使用固定常量 `MAX_CONSOLE_LOGS = 200`。历史和实时日志都进入同一个队列。刷新时：

- 合并当前窗口与待处理日志；
- 如果超过 200 条，从头部移除最旧部分；
- `logMessages` 只保存这 200 条对应的文本；
- Console DOM 也只保留这 200 条对应的 `<span>`。

待渲染队列本身也在每次入队后立即裁剪到最近 200 条，避免一帧内集中到达大量 SSE
事件时产生短时无界增长。即使旧事件在渲染前被淘汰，日志游标仍推进到已收到的最大 ID。

“复制日志”复制当前可见的最近 200 条。完整内容通过新增的“下载完整日志”链接获取，
避免复制时在浏览器中重新构造无限大的字符串。

### 批量渲染

日志事件只入队，并在尚未安排刷新时调用一次 `requestAnimationFrame`。动画帧回调使用
`DocumentFragment` 一次性追加整批节点，统一淘汰溢出的旧节点；如果自动滚动开启，
整批提交后只读取一次 `scrollHeight` 并写入一次 `scrollTop`。

这既限制长期资源占用，也避免历史批次或短时间密集日志造成逐行强制布局。

### 关闭和切换

关闭 Console 时必须：

- 增加打开版本号，使旧异步回调失效；
- 调用 `AbortController.abort()`；
- 关闭并清空 SSE；
- 取消待执行的动画帧；
- 清空待渲染队列、日志字符串、DOM 和日志游标；
- 重置活动任务信息和连接文案。

切换任务复用同一清理流程，然后开始新的打开流程。页面卸载时浏览器会回收页面资源，
不增加额外持久化逻辑。

## 错误处理

- 最近日志请求失败时，只有当前打开操作可以显示错误；主动取消不显示错误。
- SSE 出错沿用“正在重连”状态，浏览器使用事件 ID 自动续接。
- 完整日志下载失败由标准 HTTP 状态处理，不影响已打开的 SSE。
- 收到单条格式合法但 ID 不大于当前游标的日志时忽略，避免重连或竞态导致重复渲染。

## 测试

- Repository 测试覆盖“超过 200 条时只返回最新 200 条并保持正序”。
- 路由测试覆盖最近日志接口的固定上限、顺序和 404。
- 路由测试覆盖完整日志下载的附件响应、顺序、格式和 404。
- 页面资源测试覆盖 200 条常量、最近日志 URL、批量动画帧、DOM 淘汰、请求取消、
  关闭清理和完整日志下载入口。
- 现有日志分页、SSE 续接、任务删除和页面布局测试保持通过。
- 手动浏览器验证覆盖超过 200 条历史日志、实时新增淘汰、快速切换任务、关闭后释放和
  完整日志下载。

## 验收标准

- Console 打开、实时运行和切换期间，日志 DOM 节点数始终不超过 200。
- `logMessages`、待渲染队列和稳定窗口均不超过 200 条。
- 一批历史或实时日志只触发一次 DOM 批量提交和一次自动滚动。
- 关闭 Console 后不保留日志 DOM、字符串、待处理队列、历史请求或日志 SSE。
- 完整数据库日志可通过下载接口获取，内容顺序正确。
- 不引入新的前端运行时依赖或构建步骤。
