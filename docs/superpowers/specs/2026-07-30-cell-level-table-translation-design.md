# 单元格级弹性表格翻译设计

## 背景与目标

当前表格翻译把一整张表的全部可翻译文本节点放入一次模型请求。一张长表可能包含
数十个公式占位符；模型只要遗漏、拆分或改写其中一个占位符，整张表的响应就无法
安全恢复。重试耗尽后，当前代码会将整张表标记为 `failed`，渲染器因此展示原始
`table_body`，同表中已经正确翻译的单元格也会丢失。

任务数据中的第 9 张表有 86 个可翻译节点、47 个公式和约 10,998 个请求字符。
真正失败的是 `table-text-0077` 中的三个公式占位符，而不是截图中的 15℃ 密度
公式。该节点失败导致整张表回退，说明公式保护本身阻止了不安全结果，但表格翻译
的失败隔离粒度过粗。

本次将表格翻译改为：

- 单元格级公式保护；
- 受预算约束的小批量模型请求；
- 单元格级响应验收；
- 只重试失败单元格；
- 重试耗尽后只回退失败单元格；
- 在原始解析结构上生成完整、安全的 `translated_table_body`。

本次不修改普通 `text` 的翻译逻辑，不处理 MinerU 公式识别错误，也不修改前端
渲染器。

## 方案选择

采用“自适应单元格批处理 + 单元格结果回收”。

始终单单元格请求虽然隔离性最好，但会显著增加长表的模型调用量。固定小批次仍会
让一个坏单元格拖累同批其他结果。自适应方案第一轮保留批处理效率，同时逐项接收
有效结果；后续只对失败项缩小批次并重试，最终可退化为单单元格调用。

## 组件边界

表格翻译拆分为四个职责明确的组件：

1. **表格解析与重建**
   - 使用 `HTMLParser` 事件构建轻量解析树和单元格记录；
   - 识别 `table`、`tr`、`td`、`th`、`caption` 及嵌套内联元素；
   - 保存原始标签、属性、文本位置和单元格内部结构；
   - 最终只在原始 HTML 的已解析内容范围内倒序写回，不重新生成外层标签。

2. **单元格内容保护**
   - 提取可见文本；
   - 保护公式与内联结构；
   - 判断是否需要翻译；
   - 对超长内容创建安全 segment；
   - 校验并恢复模型返回内容。

3. **批次规划与模型协议**
   - 按 token 估算、单元格数量和公式数量建立批次；
   - 为每批生成 JSON 请求和严格 JSON Schema；
   - 对有效响应逐单元格验收，不把局部错误扩大为整批失败。

4. **重试与结果汇总**
   - 保存已经成功的单元格；
   - 仅重新规划失败 work item；
   - 最后一轮强制单项调用；
   - 汇总成功、回退和错误信息，生成完整译表。

这些组件属于 `table_translation.py` 及其相邻的聚焦模块。普通段落继续使用现有
`FormulaProtectionContext` 和 `_translate_one()`，不改变请求、重试或状态语义。

## HTML 解析与单元格身份

不得使用正则或字符串切割发现 `<td>`、`<th>`。解析器从原始 `table_body`
构建轻量 DOM 记录，并继续执行现有的标签闭合、结束标签匹配和最终结构比较。

每个 `td`、`th`、`caption` 按文档顺序分配稳定 ID：

```text
cell-0001
cell-0002
...
```

每个单元格记录：

- 标签名及属性；
- 内容起止位置；
- 可见文本节点；
- `<br>`、列表项和内联标签位置；
- 原始内部 HTML；
- 公式保护映射；
- segment 列表；
- 翻译状态和最后一次错误。

`table`、`tr`、`td`、`th`、`caption`、`colspan`、`rowspan` 及其他原始属性
不会发送给模型，也不会由模型重建。

## 内联结构保护

单元格可能包含 `<br>`、`em`、`strong`、`sup`、`sub`、列表等内部结构。
模型只看到可见文本和短结构标记，不看到原始标签文本。

简单文本单元格作为一个逻辑内容处理。存在内联标签时，解析器把原始开始标签、
结束标签和自闭合标签保存到本地映射，并在模型文本中使用单元格局部短标记，例如：

```text
⟦H0⟧Mass⟦H1⟧ Fraction
```

恢复时要求结构标记数量、集合、唯一性和顺序一致，再把本地保存的原始标签逐字
放回。任一结构标记校验失败只使当前单元格失败。最终 HTML 仍要通过现有结构对比。

`<br>` 和列表项优先作为 segment 边界；它们的原始标签和属性保存在本地，不能
被模型改写。

## 单元格局部公式保护

表格不再使用请求级长占位符。每个单元格创建独立公式上下文，并从零局部编号：

```text
⟦M0⟧
⟦M1⟧
...
```

裸 `M0` 容易与正文碰撞，因此必须带固定哨兵边界。每个单元格可重复使用
`⟦M0⟧`，因为模型结果由 `cell_id` 绑定到对应的本地上下文。

本地公式记录包含：

- 公式局部 ID；
- 包含 `$` 或 `$$` 边界的完整原始字符串；
- SHA-256；
- 当前单元格中期望的顺序。

哈希不放入模型占位符。模型永远看不到原始 LaTeX。恢复时独立校验：

- 占位符数量；
- ID 集合；
- 重复或新增 ID；
- 占位符顺序；
- 哨兵和 ID 是否被篡改；
- 模型是否新增公式；
- 恢复后公式数量、顺序、逐字内容和 SHA-256。

任一校验失败只影响当前单元格或当前 segment。

## 跳过规则

以下单元格不进入模型，直接保留原始内容：

- 空白单元格；
- 纯数字、数值范围、百分数及标点；
- 纯公式；
- 完全由标准编号和允许分隔符组成的内容。

标准编号规则必须保守，只匹配整个单元格，例如 ASTM/IP/UOP 方法编号、设备编号
或它们的纯分隔列表。包含 `or`、`and`、说明文字或其他自然语言的内容仍要翻译。
例如：

- `D1298`：跳过；
- `D1298 / IP 160`：可跳过；
- `D1298 or IP 160`：需要翻译，因为包含自然语言连接词。

现有中文文本和没有英文字母的内容继续跳过。跳过逻辑不能把公式识别或编号纠错
引入本次范围。

## 批次预算

按原始单元格顺序使用贪心算法建立第一轮批次。一个批次同时受三个上限约束：

- 最多 12 个 work item；
- 最多约 2,000 个估算输入 token；
- 最多 24 个公式占位符。

任一上限将被超过时开始新批次。无单独 tokenizer 依赖，使用保守估算：

- ASCII 字符按约 4 字符/token；
- CJK 字符按 1 字符/token；
- JSON 字段、ID 和固定提示加入常量开销；
- 占位符和结构标记按其实际字符计入。

这些值先作为模块内部常量，不新增环境变量。测试锁定预算边界，以便后续根据真实
模型数据调整。

表格内批次顺序执行，避免在现有跨表并发之上再叠加无界并发。不同表仍沿用当前
`ThreadPoolExecutor` 并发。

## 超长单元格与 segment

若一个单元格单独就超过 token 预算，按以下优先级切分：

1. `<br>` 和列表项边界；
2. 句末标点；
3. 空白及其他安全文本边界。

切分在公式和结构保护后执行。边界检测把 `⟦M...⟧`、`⟦H...⟧` 视为不可分割
token，禁止从其内部切断。无法找到安全边界时，允许该 segment 单独超过软 token
预算，不做破坏性硬切。

segment 在模型协议中仍使用 `cell_id` 字段，但 ID 扩展为：

```text
cell-0001:segment-0001
```

每个 segment 独立验收和重试。只有同一单元格的全部 segment 都成功，才按原始
顺序合并并恢复该单元格。任一 segment 最终失败，整个单元格回退 MinerU 原文，
避免单元格内部中英文混杂。

## 模型请求与结构化响应

每批请求只包含当前 work item：

```json
{
  "task": "Translate each cell text to Simplified Chinese and preserve markers.",
  "cells": [
    {
      "cell_id": "cell-0001",
      "text": "Density at ⟦M0⟧"
    }
  ]
}
```

模型只能返回：

```json
{
  "cells": [
    {
      "cell_id": "cell-0001",
      "translated_text": "密度在 ⟦M0⟧ 时"
    }
  ]
}
```

每批动态生成严格 JSON Schema：

- `cell_id` 只能来自当前批次；
- `translated_text` 必须是非空字符串；
- 每项和顶层对象禁止额外字段。

本地校验不能依赖服务端严格模式。顶层不是有效 JSON、`cells` 不是数组等错误会让
当前批所有 work item 进入重试。顶层结构有效时逐项处理：

- 正确且唯一的期望 ID：独立校验译文和占位符，成功后立即保存；
- 缺失 ID：仅该 work item 失败；
- 重复 ID：仅对应 work item 失败；
- 空译文或字段类型错误：仅对应 work item 失败；
- 未知新增 ID：丢弃并记录批次 warning，不影响其他期望 ID；
- 公式或结构恢复失败：仅对应 work item 失败。

即使同一批部分返回项无效，已经通过全部校验的 work item 也不能被再次发送或丢弃。

## 自适应重试

模型总尝试轮数继续使用 `max_retries + 1`。

第一轮按初始预算批处理。每轮结束后只收集尚未成功的 work item。后续批次的单元格
上限按轮次减半；最后一轮无条件强制单 work item 请求。

因此当前默认 `max_retries=1` 时流程为：

```text
小批量第一轮 -> 失败 work item 单独重试
```

若以后增加重试次数，则表现为：

```text
初始批次 -> 更小批次 -> ... -> 最后一轮单项
```

HTTP 错误、空响应和顶层 JSON 错误会使该批所有未成功 work item 进入下一轮。
单项最终失败后不再影响其他结果。

模型调用次数按真实批次数累计。日志记录表号、批次号、轮次、work item 数量、
成功数、失败数和安全错误摘要，不记录原始表格或完整译文。

## 单元格回退与表格状态

重试结束后：

- 成功的普通单元格写回译文；
- 成功的分段单元格合并后写回；
- 跳过的单元格保留原始内容；
- 任一 segment 最终失败的单元格整体保留原始内部 HTML；
- 普通失败单元格保留原始内部 HTML。

只要原始 HTML 可解析，并且成功生成通过结构校验的完整
`translated_table_body`，表格写为 `translation_status=success`。这里的
`success` 表示“已安全生成可渲染的完整表格”，不表示所有单元格都翻译成功。

同时写入：

```json
{
  "translation_status": "success",
  "table_translation_partial": true,
  "table_translation_success_cell_count": 84,
  "table_translation_fallback_cell_count": 2,
  "table_translation_fallbacks": [
    {
      "cell_id": "cell-0077",
      "error": "公式占位符被篡改"
    }
  ]
}
```

字段语义：

- `table_translation_partial`：至少一个本应翻译的单元格最终回退；
- `table_translation_success_cell_count`：成功翻译的逻辑单元格数，不按 segment
  重复计数；
- `table_translation_fallback_cell_count`：最终回退的可翻译单元格数；
- `table_translation_fallbacks`：按单元格原始顺序记录 ID 和最后错误；
- 跳过的单元格不计入成功或回退数量。

完全成功时 `table_translation_partial=false`、回退数为 0、回退数组为空。
没有可翻译单元格时仍生成原始 `translated_table_body`，状态为 `success`，成功和
回退数量均为 0。

只有以下表级错误继续标记整表 `failed`：

- `table_body` 为空或不是字符串；
- HTML 无法解析、标签不平衡或缺少 `table`；
- 最终写回后 HTML 结构校验失败；
- 无法构造安全的完整 `translated_table_body`。

这样无需修改现有渲染器。渲染器继续使用 `success` 的
`translated_table_body`，其中失败单元格已经在后端安全回退为原文。

## 断点恢复

已有 `success` 表格继续按当前行为跳过。新生成的部分成功表格也属于安全的
`success`，再次运行不会自动重试其中的回退单元格。

本次不增加“只重试部分成功表格中的失败单元格”的跨任务断点协议。该能力需要保存
足够的单元格映射和版本信息，属于后续独立范围。当前任务内的所有重试仍会完成，
并记录最终回退信息。

## 测试

单元测试覆盖：

- HTML 解析器按 `td`、`th`、`caption` 生成稳定 `cell_id`；
- `table`、`tr`、`td`、`colspan`、`rowspan` 和内联标签不进入模型；
- `⟦M0⟧` 在每个单元格独立编号并逐字恢复公式；
- 多公式单元格的缺失、重复、新增、篡改和顺序变化；
- 内联结构标记恢复及篡改失败；
- 空、纯数字、纯公式和纯标准编号跳过；
- 包含自然语言的编号列表不会误跳过；
- 三项批次预算分别触发分批；
- 有效部分响应被保留，缺失或重复 ID 只影响对应 work item；
- 未知 ID 不污染合法单元格；
- 重试只包含失败项，批次逐步缩小，最终单项；
- HTTP、空响应和顶层 JSON 错误只重试对应批；
- 超长单元格按 `<br>`、列表、句子和安全边界分段；
- segment 不切断公式或结构标记；
- 任一 segment 最终失败时整个单元格回退；
- 单元格回退不影响同表其他成功译文；
- 最终 HTML 标签、属性、顺序和结构保持一致；
- 部分成功表格状态、计数和错误明细正确；
- 完全成功、无需翻译和表级解析失败的状态正确。

集成测试使用任务数据中的规模模式构造长表，证明一个包含三个公式的后部单元格
失败时：

- 前面包含 15℃ 公式的密度单元格译文仍保留；
- 失败单元格回退原文；
- `translated_table_body` 仍生成；
- 表格状态为安全 `success` 且 `table_translation_partial=true`；
- 现有渲染器会使用该部分译表。

最后运行完整 pytest 和包构建，确认普通文本翻译、MinerU 清理、断点、并发、Web
和前端渲染行为不受影响。
